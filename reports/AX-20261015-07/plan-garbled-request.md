AX-20261015-07 지시안

1. 목적 / 완료 조건

WMS 다운로드가 반복 실패할 때, 기존 디버깅 Chrome의 WMS 화면을 제한적으로 새로고침하여 다음 회차에서 복구하도록 한다.

요청문이 깨져 있어 **연속 실패 3회, 새로고침 간격 최소 15분**을 잠정 기준으로 제안한다. 정확한 기준은 확인이 필요하다.

완료 조건:

- 정상 회차에서는 새로고침하지 않는다.
- 일시적 실패와 지속 실패를 구분하고, 지속 실패 시에만 WMS 원래 창에서 `driver.refresh()`를 호출한다.
- 새로고침 실패도 기록하고 반복 루프를 유지한다.
- 브라우저 세션 단절은 기존 재연결 분기로 처리한다.
- URL 직접 이동, 로그인 자동화, DB 변경을 추가하지 않는다.
- 기존 조회 조건·기준선·재확인 회차의 동작을 보존한다.

3. 작업 단계

① Claude가 원문 요청과 이 계획을 대조하고 `plan-check.md`에 기준을 확정한다.

② `run_forever()`에 회차 단위 연속 실패 횟수와 마지막 새로고침 시각을 추가한다.

- 한 회차에서 여러 조회가 실패해도 실패 횟수는 한 번 증가한다.
- `False` 반환과 예외 종료를 모두 실패로 집계한다.
- 모든 조회가 성공한 회차에서 연속 실패 횟수를 초기화한다.
- 팝업 내부 재시도 횟수와 회차 실패 횟수를 구분한다.

③ 새로고침 대상인 **원래 WMS 창 핸들**을 명시적으로 보존한다.

`run_download_macro()`는 정상 경로에서 원래 창으로 복귀하지만(`:713`), 다운로드관리자 처리 중 예외가 나면 복귀하지 못할 수 있다. 현재 선택된 창을 그대로 새로고침 대상으로 사용하지 않는다.

- 보존한 WMS 핸들로 전환한 뒤 새로고침한다.
- 핸들이 사라졌으면 기존 세션 단절 복구로 넘긴다.
- 임의의 다른 탭을 선택하거나 URL을 추측하지 않는다.
- `clear_stray_popups()`가 현재 창 외 창을 닫으므로, 복구 과정에서 이 함수를 호출하기 전에도 WMS 창 선택을 보장한다.

④ 연속 실패 기준과 최소 간격을 모두 충족하면 새로고침을 한 번 시도한다.

- 간격 계산에는 `time.monotonic()`을 사용한다.
- **시도 직전에 시각을 기록**하여 새로고침 자체가 실패해도 연속 호출을 막는다.
- 페이지 로드 대기에는 유한한 제한을 둔다.
- 새로고침 후 다운로드를 즉시 중복 실행하지 않고 다음 회차에서 메뉴 진입·검색 조건 설정부터 수행한다.
- 새로고침 성공만으로 다운로드 연속 실패 횟수를 초기화하지 않는다.

⑤ 예외 처리 우선순위를 유지한다.

- `_is_dead_session_error()`에 해당하면 기존 재연결 분기를 우선한다.
- 새로고침 중 세션 단절이 발생해도 동일하게 처리한다.
- 다른 새로고침 오류는 기록하고 기존 회차 대기로 진행한다.
- 메뉴 진입 실패 시 로그인 확인 안내를 유지한다. 로그인 화면이라는 단정은 피한다.

⑥ 로그와 docstring을 보완한다.

로그에는 회차, 연속 실패 횟수, 새로고침 시도·성공·실패, 간격 제한으로 건너뛴 이유를 남긴다. 예외 종류와 실패 단계도 기록하되 URL 전체·쿠키·인증정보는 출력하지 않는다.

`run_forever()` docstring에는 기존 세션의 화면 새로고침과 포트 9222 재연결을 구분하고, 로그인 만료는 사용자 재로그인이 필요함을 설명한다.

4. 검증 방법

실제 WMS에 연결하지 않는 가짜 driver와 가짜 시계로 회차 제어를 검증한다. 테스트 파일은 신규 추가 대상이며 현재 존재하는 파일로 간주하지 않는다.

필수 사례:

- 정상 회차 반복 → 새로고침 0회.
- 기준 미만의 연속 실패 → 새로고침 0회.
- 실패 기준 도달 → WMS 핸들 선택 후 정확히 1회.
- 15분 미만 추가 실패 → 추가 새로고침 없음.
- 15분 경과 후 지속 실패 → 다시 1회 허용.
- 실패 사이 완전 성공 → 실패 횟수 초기화.
- 일부 조회만 성공하거나 `False` 반환 → 회차 실패로 집계.
- 다운로드관리자 창에서 예외 → 관리자 창을 새로고침하지 않음.
- 새로고침 실패 → 로그 기록 후 루프 지속, 간격 제한 유지.
- 세션 단절 → 기존 재연결 분기 실행.
- 기준선 실패 → 완료 플래그 미생성.
- 기존 재확인 주기와 두 날짜 기준 조회 유지.

Claude 실행 명령:

```powershell
py -B -m unittest discover -s "UPH 시스템/tests" -v
```

운영 표본에서는 새로고침 시각, 이후 첫 정상 다운로드 시각, 감시 폴더의 새 파일 생성과 watchdog 처리 완료를 함께 확인한다. **DB의 `MAX(detected_at)`만으로 복구를 판정하지 않는다.**

이번 조사에서는 코드 읽기와 Git 상태 확인만 수행했다. 테스트 실행·실제 WMS 조작·DB 접근은 수행하지 않았다.

5. 위험 요소

- 요청이 이미 접수된 상태에서 재시도하면 다운로드 요청이 중복될 수 있다. 기존 팝업 재시도는 그대로 두고 새 복구 경로의 즉시 재실행을 피한다.
- 잘못된 창 선택과 기존 잔여 창 정리가 결합하면 WMS 원래 창을 닫을 수 있다. 핸들 보존을 우선 구현한다.
- 로그인 만료는 새로고침으로 해결되지 않을 수 있다. 기존 안내와 호출 간격 제한이 필요하다.
- 새로고침으로 검색 조건이 초기화될 수 있으므로 다음 회차에서 조건을 반드시 다시 설정한다.
- 운영 DB 스키마 변경이나 데이터 삭제는 이 계획에 포함되지 않는다.

6. 확인이 필요한 질문

- 새로고침 대상은 다운로드 전 사용하던 WMS 원래 창으로 한정하는 해석이 맞는가?
