AX-20261015-07 — Claude Code 작업 지시서

### 1. 목적 / 완료 조건

현재 로그인된 WMS 탭을 재사용하면서, 회차 실패 또는 장시간 무성공 상태를 다음 회차 전 `driver.refresh()`로 복구한다.

- 비세션 오류로 회차가 실패하면 다음 회차 시작 전에 새로고침한다. `False` 반환도 실패에 포함한다.
- 마지막 **전체 회차 성공** 이후 900초 이상 지나면 다음 회차 전 새로고침한다. 성공 이력이 없으면 프로세스 시작 시각을 기준으로 한다.
- 새로고침 후 페이지 준비를 제한 시간 동안 기다린다. 로그인 화면이면 `[ERR]`로 재로그인 필요를 알리고 다운로드·자동 새로고침을 정지한다.
- 연속 성공 중에는 새로고침하지 않는다.
- 새로고침 시각·사유·직후 회차 결과를 연결해 로그로 남긴다.
- 기존 세션 재연결, 기준선, 재확인 일정과 조회 조건을 보존한다.
- 실제 브라우저·WMS 없이 가짜 driver와 시계로 검증한다.

파일·DB 수정 및 테스트 실행은 이번 Codex 작업에서 수행하지 않았다.

### 3. 작업 단계

1. **지시서 검증 및 변경 범위 확정**
   - 위 위치를 다시 대조하고 `reports/AX-20261015-07/plan-check.md`에 수용·수정·거부 근거를 기록한다.
   - 기존 작업 트리의 `ax/lib.ps1` 변경을 보존한다.
   - 로그인 화면의 실제 식별 기준을 확인한다. 메뉴 부재만으로 로그인 화면이라고 판정하지 않는다.

2. **작은 복구 상태와 판단 헬퍼 추가**
   - 경과 시간은 `time.monotonic()`, 표시 시각은 기존 `log()`를 사용한다.
   - 시작 시각, 마지막 전체 성공 시각, 비세션 실패 여부, 마지막 새로고침 시각, 연속 복구 횟수, 로그인 대기 여부를 관리한다.
   - 판단 조건은 `비세션 실패 예약 OR 무성공 900초 이상`으로 한다. 두 조건이 동시에 참이어도 한 번만 새로고침한다.
   - 제한 기본안은 **최소 간격 90초, 전체 성공 없이 최대 3회**로 한다. 한도에 도달하면 명확한 `[ERR]` 후 사람 조치를 기다린다. 전체 성공 시 연속 횟수를 초기화한다.
   - 새로고침 시 마지막 성공 시각을 갱신하지 않는다.

3. **회차 시작 전 복구 게이트 삽입**
   - `run_forever():848`의 `try` 내부, 조회 실행 전에 둔다.
   - 저장한 원래 WMS 핸들로 전환하고 `driver.refresh()`를 호출한다. `driver.get()`, 새 탭 생성, 자동 로그인은 추가하지 않는다.
   - `document.readyState`와 확인된 WMS 화면 요소를 함께 기다린다. 로그인 화면·WMS 준비 완료·시간 초과를 구분하고, 대기에는 상한을 둔다.
   - 로그인 감지 시 `[ERR] WMS 로그인 세션 만료 — 디버그 크롬에서 재로그인 필요`를 남긴다. 이후에는 기존 간격으로 화면만 확인하며 새로고침·조회는 하지 않는다. 인증된 WMS 화면을 확인한 뒤 재개한다.
   - 새로고침 중 죽은 세션 예외는 삼키지 않고 기존 `_is_dead_session_error` 경로로 전달한다.

4. **회차 결과와 예외에 복구 상태 연결**
   - 모든 조회가 성공한 경우에만 마지막 성공 시각을 갱신한다. 일부 조회만 성공한 경우는 회차 실패다.
   - `:863`의 `False` 반환 실패, `:890`의 메뉴 실패, `:899`의 일반 오류에 다음 회차 복구를 예약한다.
   - `:871`의 죽은 세션은 기존 재연결을 우선한다. 해당 예외 자체로 새로고침을 예약하지 않는다. 기존 무성공 조건이 남아 있더라도 재연결 직후 같은 회차에서 추가 새로고침하지 않는다.
   - `run_download_macro():705`에서 예외가 나면 다운로드관리자에 포커스가 남을 수 있다. 원래 핸들 복귀를 `finally`로 보장하되, 정리 오류가 원래 예외를 가리지 않게 한다. 다른 사용자 탭을 일괄 닫지 않는다.

5. **재확인 일정 보존**
   - 현재 재확인 회차는 정상 2개와 과거 조회 2개, 총 **4개 조회**다(`:827`, `:839`, `:841`). docstring의 “세 번째 추가” 설명과 다르므로 실제 코드를 기준으로 한다.
   - 실제 조회를 시도한 재확인 회차는 성공·실패 모두 기존처럼 다음 주기로 미룬다.
   - 로그인 대기·복구 제한 등으로 조회 자체를 시작하지 않은 경우에는 재확인 시각과 기준선 완료 플래그를 갱신하지 않는다. `recon_attempted` 등 명시적 상태로 구분한다.
   - 조회 날짜·상태·CS 필터, 팝업 내부 재시도, `RECON_INTERVAL_SEC`는 변경하지 않는다.

6. **로그·테스트·인수인계**
   - 새로고침마다 식별번호, 사유, 대상 회차, 마지막 성공 후 경과 초, 연속 시도 횟수를 남긴다.
   - 같은 식별번호로 직후 회차의 `성공/실패/세션 끊김/로그인 차단/준비 시간 초과`를 기록한다. 부분 성공을 복구 성공으로 표시하지 않는다.
   - 테스트 후 HANDOFF에 코드 완료·테스트 결과·매크로 재시작 여부를 구분해 기록한다. 실행 중인 매크로는 재시작 전까지 변경이 반영되지 않는다.

### 4. 검증 방법

가짜 driver·가짜 시계·로그 수집기를 사용해 다음을 검증한다.

| 조건 | 기대 결과 |
|---|---|

| 성공 이력 없음 | 시작 시각 기준 900초 적용 |
| 정상 연속 성공 | 새로고침 0회, 기존 조회 순서·횟수 유지 |

### 5. 위험 요소

- **운영 DB 스키마 변경·대량 쓰기·외부 메시지 발송은 필요 없다.** 해당 작업이 추가로 필요해지면 별도 승인 대상으로 분리한다.
- 로그인 식별 기준은 미확인이다. 메뉴 부재만으로 판정하면 느린 화면을 세션 만료로 오인할 수 있다.
- 새로고침 대상 핸들이 틀리면 다운로드관리자나 다른 탭을 갱신할 수 있다.
- 다운로드 요청이 서버에 접수된 뒤 실패한 경우 다음 회차 재실행으로 중복 파일이 생길 수 있다. 이번 변경에서 요청 횟수를 추가로 늘리지 않는다.
- 현재 다운로드 생성 완료 대기는 무제한이라는 설명이 있다(`:203`). **15분 규칙은 다음 회차 경계에서만 평가하므로 진행 중인 무한 대기를 끊지는 못한다.** 이를 해결하려면 별도 범위가 필요하다.
- 새로고침으로 서버 측 장애가 해결된다는 보장은 없다. 제한 횟수와 결과 로그로 효과를 검증한다.
- 실제 운영 재시작 시 수집 공백·중복 프로세스 실행에 주의한다. 허브 전체 종료는 다른 UPH 자식 프로세스에도 영향을 줄 수 있다.
- 로그에 전체 URL·쿠키·페이지 원문·계정 정보를 남기지 않는다. commit/push는 저장소 규칙에 따라 사용자 확인 후 수행한다.

### 6. 확인이 필요한 질문

1. 실제 로그인 화면을 확정할 URL 패턴 또는 표시 요소는 무엇인가? 현재 코드만으로는 확인할 수 없다.
2. 자동 복구 기본값인 **90초 간격·연속 최대 3회**, 이후 사람 조치 대기 정책을 채택할 것인가?
3. 성공 이력이 없을 때 **프로세스 시작부터 15분**을 적용하고, 로그인 차단 후에는 사람이 로그인한 것을 감지해 자동 재개하는 방식이 적절한가?
