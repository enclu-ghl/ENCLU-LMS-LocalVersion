**1. 목적 / 완료 조건**

`process_file()`의 읽기 실패 파일을 다음 폴링에서 제한적으로 재시도한다.

- 제안 기본값: **최초 시도 포함 최대 3회**. 같은 폴링 안에서 즉시 반복하지 않는다.

- 세 번째 읽기 실패 시 파일명·시도 횟수·재시도 중단을 명시한 `ERROR`를 남기고 processed로 처리한다.
- 재시도 대기 파일은 cleanup 삭제 대상에서 제외한다.
- 읽기 이후 DB push·캐시 갱신·예외 전파의 기존 동작을 유지한다.
- 실제 함수에 실패를 주입한 테스트로 일시 실패 후 성공, 영구 실패, cleanup 보호를 검증한다. 운영 DB와 실제 WMS 파일은 사용하지 않는다.

**3. 작업 단계**

1. Claude가 현재 코드와 본 지시서를 대조하고 `reports/AX-20261015-04/plan-check.md`에 수용·수정·거부 근거를 기록한다. 기존 사용자 변경은 보존한다.

2. `process_file()` 반환값을 다음처럼 명확히 정의한다.
   - `False`: 기존 `read_wms_file()` 호출의 `except`에서만 반환.
   - `True`: 변경분 없음 조기 종료 및 함수 정상 종료.
   - `True`의 의미는 **읽기 실패 재시도 대상이 아님**이다. DB 저장 성공을 의미하지 않는다.
   - 읽기 이후 예외를 새로 잡아서 `False`로 바꾸지 않는다. DB 부분 실패 반환과 캐시 처리 순서도 유지한다.

3. `main()`에 파일 경로별 읽기 실패 횟수 사전을 추가한다.
   - `False`이면 해당 파일 횟수만 증가시킨다.
   - 한도 미만이면 미처리 상태로 남기고 같은 회차의 다른 파일을 계속 처리한다.
   - 한도 도달 시 중단 `ERROR`를 남기고 processed에 추가한다.
   - `True`이면 기존처럼 processed에 추가한다.
   - 성공 또는 한도 도달 시 재시도 사전에서 제거한다.
   - `any_processed`는 실제 processed 추가 여부를 반영하게 한다.

4. cleanup에 보호 파일 집합을 전달하도록 변경한다.
   - 기존 최신 `keep_n`개 보존 규칙을 유지하면서 삭제 직전에 보호 집합을 검사한다.
   - 재시도 사전의 파일은 최신 보존 개수 밖이어도 삭제하지 않는다.
   - 같은 회차에서 안정화 대기 중인 미처리 파일도 보호한다.
   - 성공·한도 도달 이후에는 기존 정리 정책을 적용한다. 보호 때문에 일시적으로 보존 개수를 초과할 수 있음을 주석에 명시한다.

5. 아래 테스트를 구현·실행한다. 실제 `process_file()`과 실제 폴링 분기를 실행하고, 재시도 로직을 테스트에 복사하지 않는다.

현재 Codex는 소스 확인만 수행했으며, 위 테스트는 **미실행**이다.

**5. 위험 요소**

- **운영 DB 스키마 변경·대량 쓰기·외부 발송은 필요하지 않다.** 테스트 중 운영 watchdog을 실행하면 초기화·SKU 집계·DB 반영이 발생할 수 있으므로 반드시 격리한다.
- 반환값을 일반적인 성공/실패로 해석하면 DB push 실패까지 재시도 대상으로 확대될 수 있다. 읽기 단계만 구별해야 한다.
- cleanup 보호를 빠뜨리면 다른 파일의 정상 처리 직후 재시도 파일이 삭제될 수 있다.
- 한도 초과 파일은 의도적으로 재처리를 중단하며 이후 cleanup에서 삭제될 수 있다. 해당 파일의 변경분이 반영됐다고 기록하면 안 된다.
- 횟수와 processed 상태는 메모리에 두므로 재시작하면 초기화된다. 영구 상태 저장이나 DB 변경은 이번 범위에 포함하지 않는다.
- 파일 수정은 현재 실행 중인 watchdog에 반영되지 않는다. 운영 재시작은 별도 적용 단계이며, commit/push·운영 적용은 사용자 확인 후 진행한다.
