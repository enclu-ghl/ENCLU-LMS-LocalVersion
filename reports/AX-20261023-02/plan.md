### 3-2. 감사 결과

#### F01. 간단조사에서 전산수량 초과분 소실 — 높음

- **위치:** `app.py:1825`, `app.py:1830`, `app.py:1851`
- **문제·근거:** 기준재고가 여러 유통기한 행이면 실사수량을 각 전산수량까지만 배분한다. 마지막 행 이후 남은 `remaining`은 저장하지 않는다. 성공 메시지는 입력 수량을 표시한다.
- **재현:** 같은 상품·위치의 기준수량이 3개와 2개인 상태에서 간단조사 8개 저장. 저장 합계는 5개, 성공 메시지는 8개가 된다.
- **영향:** 실사수량 손실, 과잉재고 은폐, 잘못된 리포트.
- **수정 방향:** 입력 합계와 저장 합계의 보존을 강제한다. 간단조사 총량을 유통기한별로 추정 배분할지 업무 기준부터 결정한다.

#### F02. 유통기한 없는 정상 실사가 리포트에서 누락 — 높음 / 실행 확인

- **위치:** `app.py:2339`, `app.py:2341`
- **문제·근거:** `groupby()`의 기본 동작으로 유통기한 등 집계 키가 NULL인 행이 제외된다.
- **재현:** 기준수량 5개, 실사 5개, 양쪽 유통기한 `None`. 실제 `make_report()`를 메모리에서 실행한 결과는 **실사 0개·미조사·차이 -5개**였다.
- **영향:** 정상 실사를 미조사·부족재고로 보고.
- **수정 방향:** NULL을 포함한 집계와 키 정규화를 적용한다. NULL 위치도 함께 검증한다.

#### F03. 전체 불일치 리포트에서 세션 혼합 — 높음 / 실행 확인

- **위치:** `app.py:2324`, `app.py:2339`, `app.py:2512`, `app.py:2520`
- **문제·근거:** `make_report()`가 세션을 기준 컬럼·집계 키에서 제외한다. 불일치 화면의 “전체”는 여러 세션을 그대로 전달한다.
- **재현:** A·B 세션에 같은 바코드·위치·유통기한을 각각 기준 5개·실사 5개로 구성. 실행 결과 각 기준행에 실사 10개가 매칭되어 차이 +5개가 발생했다.
- **영향:** 허위 불일치, 세션 간 수량 및 담당자 혼선.
- **수정 방향:** 세션을 모든 매칭·집계·담당자 결합 키에 포함하거나 세션별 결과를 만든 후 합친다.

#### F04. 기준재고 중복을 허용하고 실사수량을 반복 매칭 — 높음 / 실행 확인

- **위치:** `app.py:1444`, `app.py:1453`, `app.py:2344`, `app.py:2630`
- **문제·근거:** “추가”는 중복 검사 없이 append한다. 리포트는 각 기준행에 같은 실사 합계를 반복 매칭한다. 로그 JOIN과 홈 진행률도 중복 영향을 받는다. 덤프에서 해당 업무 키의 유일성 제약은 확인되지 않았다.
- **재현:** 동일 키 기준행 5개짜리 2건에 실사 5개 1건을 전달. 실행 결과 두 행 모두 실사 5개·차이 0개였다. 로그에서는 기준행 수만큼 실사행이 복제될 수 있다.
- **영향:** 부족재고 은폐, 로그 수량 부풀림, 진행률 왜곡.
- **수정 방향:** 중복의 업무 의미를 먼저 정하고 업로드 중복 처리·리포트 집계 단위를 통일한다. 제약 추가 전 기존 중복 조사가 필요하다.

#### F05. 전수조사의 중복 유통기한 처리 불일치 — 높음

- **위치:** `app.py:1873`, `app.py:1902`, `app.py:2210`, `app.py:2231`, `app.py:2238`
- **문제·근거:** 기존 기록과 입력은 유통기한을 딕셔너리 키로 사용해 같은 날짜의 앞선 값을 덮어쓴다. 추가 입력은 기존 날짜·추가 날짜 중복을 합치지 않고 별도 INSERT한다.
- **재현:** 같은 날짜의 기준행 2건을 입력하거나, 기본 날짜와 같은 날짜를 추가 입력한 뒤 저장·재조회한다.
- **영향:** 화면 입력 합계, 저장 행, 재조회 기본값이 달라짐.
- **수정 방향:** 날짜별 합산 또는 중복 금지 정책을 통일하고 저장 전 최종 키별 합계를 만든다.

#### F06. 동시 저장은 직렬화되지만 오래된 화면의 덮어쓰기는 방지하지 못함 — 높음

- **재현:** 두 작업자가 미조사 상태를 동시에 열고 각각 다른 수량으로 저장한다.
- **영향:** 먼저 저장한 수량·작업자 정보 소실.
- **수정 방향:** 수정 버전·시각 비교 등 충돌 감지를 추가하고 재확인을 요구한다. 수량을 자동 합산하는 방식은 중복 계수 위험 때문에 별도 판단한다.

- **재현:** 두 화면에서 기준수량 10개를 열고 각각 7개씩 분할하거나, 한 화면에서 분할하는 동안 다른 화면에서 재정렬한다.

#### F08. 재정렬 후 기존 실사 유통기한이 그대로 남음 — 중간

#### F14. 같은 세션 덮어쓰기와 세션 재사용이 과거 실사를 혼입 — 높음

- **재현:** S 세션 실사 후 같은 이름으로 다른 기준을 덮어쓰거나, 기준만 삭제 후 같은 이름으로 재업로드한다.
- **영향:** 조사 완료 오판, 과거·현재 데이터 혼합, 리포트 누락.
- **수정 방향:** 조사 회차와 기준 버전을 분리하고 재업로드 정책을 정한다. 같은 이름에 자동으로 과거 실사를 연결하지 않도록 한다.

- **수정 방향:** 기준재고 기반 정책으로 UI를 정리하거나 공유·영속 세션 모델을 설계한다. 세션명 공백 정규화도 함께 수행한다.

#### F16. 오류 스캔에 세션·위치가 없고 필터도 적용되지 않음 — 중간

#### F19. KST 표시가 DB 세션 타임존에 의존 — 중간 / 조건부

## 4. 검증 방법

### 실제 수행

- 지정 규칙 문서와 프로젝트 가이드를 읽었다.
- 대상 저장소의 `git remote -v`, `git rev-parse HEAD`, `git status --short`를 확인했다.
- 재고조사 `app.py:1231`부터 `app.py:2702`까지와 관련 헬퍼·진입 코드를 읽었다.
- SQL 덤프의 테이블 정의와 관련 제약을 확인했다.
- `ast.parse()`로 실제 `make_report()` 함수만 추출하여 메모리 합성 데이터로 실행했다. 앱 전체는 실행하지 않았다.
- 실행 재현 결과: **NULL 유통기한 누락, 세션 혼합, 중복 기준행의 실사 반복 매칭**을 확인했다.

### Claude 추가 검증 표

운영 DB·실제 앱에서 쓰기 버튼을 누르지 않는다. 이번에는 정적 대조와 DB 없는 계산·모의 객체 검증까지만 수행한다.

| 표본 | 확인할 기대 조건 |
|---|---|
| 기준 3+2, 간단조사 8 | 입력 8과 저장 합계가 일치 |
| NULL 날짜, 기준·실사 각 5 | 조사완료·차이 0 |

- 실제 업무 파일 형식·최대 규모·성능.
- 기존 잘못된 데이터의 존재 및 규모.
- 수정 후 테스트 파일·함수: **미확인**. 이번 감사에서는 생성하지 않았다.

## 5. 위험 요소

- **운영 DB 스키마 변경:** 감사에는 필요 없다. 업무 키 제약, 오류 세션 컬럼, 변경 이력, 타임존 타입 도입은 별도 설계·승인이 필요하다.
- **대량 쓰기·삭제:** 이번 작업에서는 금지한다. 중복 병합·과거 실사 보정·시각 일괄 변환은 데이터 손실 위험이 있으므로 영향 목록·백업·복구 계획이 선행되어야 한다.
- **트랜잭션:** 업로드 덮어쓰기·초기화·실사 저장은 이미 `engine.begin()`을 사용한다. 문제를 일괄적으로 “트랜잭션 누락”으로 분류하지 않는다. 주된 위험은 의미상 데이터 연결과 동시성 검증 부족이다.
- **회귀:** 중복 처리·간단조사 배분 정책을 바꾸면 기존 리포트 결과가 달라질 수 있다. 기준 합계·실사 합계 보존을 검증해야 한다.
- **외부 발송·배포:** 감사에 필요 없으며 수행하지 않는다. 문서상 웹앱 push는 Streamlit Cloud에도 영향을 줄 수 있으므로 후속 수정의 배포는 별도 승인 대상이다.
- **민감정보:** 접속정보·업무 원본·작업자 실명·덤프 데이터를 감사 문서나 공개 저장소에 복사하지 않는다.
