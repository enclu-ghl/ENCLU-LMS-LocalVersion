# AX-20261015-05 — 감사 F2 작업 지시서

## 1. 목적 / 완료 조건
`_local_db/verify_migration.py`가 Supabase 해지 전 최종 검증으로 쓸 만큼 정확하도록 한다.
- 대상(로컬)에만 있는 테이블을 보고한다(정보, 실패 아님).
- 원본에만 있는(대상에 없는) 테이블은 명확히 실패로 보고한다.
- 테이블별 컬럼 구성(이름·타입)을 비교해 다르면 실패.
- 행수 규칙: 같으면 OK / 대상 < 원본이면 실패 / 대상 > 원본이면 "증가":
  - 정수형 `id` 컬럼이 양쪽에 있으면, 원본의 `MIN(id)~MAX(id)` 범위 안에 대상 행이 원본 행수 이상 있는지 확인 → 충족 시 "증가(정보)", 미충족 시 실패.
  - `id`가 없으면 "증가(확인 필요)" — 기본은 정보, `--strict`면 실패.
- 종료코드 의미 유지: 실패 0건이면 0, 아니면 1. 기존 테스트 5개 유지 + 확장 테스트.

## 2. 근거 (현재 코드, 직접 확인)
- `verify_migration.py:17-47` `compare()` — 원본 `pg_tables` 목록 기준 COUNT(*)만 비교.
- 전환 후 로컬에서 계속 쌓이는 테이블(`order_status_log`, `manpower_log` 등)은 대상 > 원본이 정상. 현재 규칙으로는 무조건 `!!`(실패) → 해지 전 검증에서 의미 없는 실패가 섞여 진짜 누락을 가린다.

## 3. 원본(Supabase) 부하 제한 — 저사양 인스턴스 다운 사고 이력
원본에는 `pg_tables`/`information_schema.columns` 조회, 테이블별 `COUNT(*)`(기존과 동일), 정수 `id`의 `MIN/MAX`(PK 인덱스)만 보낸다.
범위 안 행수 세기(`COUNT(*) WHERE id BETWEEN`)는 **대상(로컬)에서만** 실행한다. 전체 해시·전체 스캔 비교는 하지 않는다.

## 4. 작업 단계
1. `compare(src, dst, strict=False)`로 확장, 출력에 상태 열(OK / 증가 / !!)과 사유.
2. 헬퍼: 테이블 목록, 컬럼 맵(`information_schema.columns`, `table_schema='public'`), id 범위 확인.
3. `main()`에 `--strict` 인자.
4. 테스트(SQLite): `pg_tables`·`information_schema.columns` 흉내(연결 시 ATTACH). 케이스 — 일치 / 행수 부족 / 대상 테이블 누락 /
   대상 전용 테이블(정보) / 컬럼 불일치 / 증가+id 범위 충족 / 증가+id 범위 안 누락(실패) / id 없는 증가(기본 정보, strict 실패) / main 종료코드.

## 5. 위험
- 운영 DB 쓰기 없음(SELECT만). 실제 Supabase 대상 실행은 하지 않는다(해지 직전 사용자 확인 후 실행).
- 범위 확인은 "원본 범위 안 행수 ≥ 원본 행수"로 보는 근사 — 같은 수만큼 다른 행으로 바뀐 경우는 못 잡는다(한계로 출력·문서에 명시).
