# AX-20261029-01 요청 — 송장 시스템 설계 (설계 지시서만, 코드 변경 없음)

웹앱(`웹으로 진행 중인 건/app.py`, Streamlit, 운영 DB = 서버 PC 로컬 PostgreSQL)에 송장 기능을 넣기 위한 **설계안**을 만든다.
이번 작업은 설계만 한다: 데이터 모델(표·컬럼·키), 화면 흐름, 외부 연동 경계, 단계 나누기, 위험, 사용자에게 확인할 질문.

## 사용자 답변 (2026-10-29, 원문 요약)
### 택배사·출력
- 1차: 일본 배송, **KSE 배송사 OMS** 기준으로만. 차후 배송사별 집계·출력으로 확장 가능한 구조여야 함.
- 현재 송장은 KSE OMS에서 출력. 택배사(KSE) **API 연동 가능**.
### 주문 경로
- 전체 플랫폼 주문은 WMS **이지어드민**에 모이며 엑셀로 다운로드.
- 송장번호는 다시 이지어드민 WMS에 **엑셀 업로드**로 반영.
### 물량·장비
- 평소 하루 1,000건 이하, 최대 약 30,000건.
- 프린터: XPRINT(XP-D4601B, XP-DT427B), TSC(TTP-384MT). 사무동에 XPRINT 8대·TSC 2대, 각 출고동에 XPRINT 1대(90×60).
- 용지: 기본 송장 90×60, 라벨 송장 60×40, A4 4장형·8장형.
- 바코드 스캐너 충분.
### 검수
- 출력 전 검수(프린터 확인, 시책 검증 등 출력·전산 반영 문제 점검) 후 출력 + 출력 후 전수 검수(오출고 방지 스캔).
- 출력 후 검수는 WMS 연동 스캔 프로그램이 송장 스캔 → 상품 단위 스캔으로 이미 수행, 오류 시 그 프로그램이 정지함.
  → 우리 시스템 범위는 **출력 전 검수**. 스캔 오류는 기록을 받을 수 있으면 기록만.
### 합포장·재출력·취소
- 합포장: 같은 주문상세번호·수령인·주소·연락처·판매처 → **OMS가 같은 송장번호로 묶음**.
- 출력 시 **출력 횟수 카운트**. 재출력 시 **경고 모달**. 재출력 사유 지정(동: 용지 걸림·박스 변경·송장 파손 / 사무: 시책 미적용·출력 문제 등), **사유별로 카운트 포함 여부** 설정.
- 송장 등록에 이상이 있으면 OMS에서 전부 삭제 후 재등록하는 경우가 있음 → OMS API와 동기화가 정확해야 함(삭제·재등록 반영).
- 취소: 취소 건은 OMS에서 삭제 처리 → 그 반영만. 반품 송장은 이번 범위 아님.

## 설계 시 반드시 다룰 것
1. 기존 코드·DB 확인: 재고할당(WMS 파일 업로드·`alloc_*` 표), 주문파일정리, 출고 로그(`outbound`/요약 보존) 중 재사용할 것과 겹치는 것.
2. **누가 실제로 출력하는가**: (a) 우리 시스템이 KSE API에서 송장 데이터/이미지를 받아 프린터로 직접 출력 vs (b) 출력은 KSE OMS가 하고 우리는 기록·검수만. 출력 횟수·재출력 모달 요구는 (a)를 전제하는 것처럼 보임 — 각각의 실현 가능성(Streamlit은 서버에서 돌고 프린터는 각 PC/동에 있음, 브라우저 인쇄 vs 서버/로컬 인쇄 에이전트, TSPL/ESC 원시 출력, 용지 크기별 프린터 지정)과 비용을 비교.
3. 3만 건/일 규모에서의 성능: API 호출 속도 제한·일괄 처리, DB 일괄 upsert(행 단위 반복 INSERT 금지 — 과거 장애 이력), 화면 렌더링.
4. 배송사 확장: 배송사 코드를 1급 키로 두는 모델.
5. 이지어드민 업로드용 엑셀 양식 생성(송장번호 반영).
6. 상태 머신: 주문 수신 → 송장 발급(OMS) → 출력 전 검수 → 출력(횟수) → 재출력(사유) → 업로드 완료 / OMS 삭제·재등록 / 취소.
7. 비밀값(API 키)은 `.env`에만, 저장소 커밋 금지(공개 저장소).
8. 단계(1차 최소 기능 → 확장)와 각 단계 검증 방법.
9. 사용자에게 확인할 질문 목록(KSE API 문서·제공 항목, 시책 검증의 구체 규칙 — 2026-08 "시책 대조 프로그램 개발 취소, 수동 엑셀 체크" 결정과의 관계 등).
