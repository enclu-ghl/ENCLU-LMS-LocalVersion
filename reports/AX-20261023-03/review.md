1. **[높음] 기준재고가 없는 위치에서 다른 위치의 기준행을 수정할 수 있음**
   
   - **파일:줄:** `app.py:1953`, `app.py:2046`, `app.py:2122`
   - **문제·근거:** 입력 위치에 기준행이 없으면 `master_rows`가 다른 위치의 `[result]`로 대체됩니다. 이 행의 분할·날짜 변경 버튼도 표시되며, 수정 SQL은 `mr.id`로 원래 위치의 기준행을 변경합니다. 화면에는 입력 위치의 기준수량이 0으로 표시되어도 다른 위치 재고가 변경될 수 있습니다.
   - **확인 방법:** L1에만 등록된 상품을 전수조사에서 검색하고 위치를 L2로 입력한 뒤, 날짜 변경 또는 분할을 실행합니다. L1의 기준행이 변경되는지 임시 DB에서 확인합니다.
   - **제안:** 기준행이 없는 위치에서는 다른 위치 행의 편집 UI를 표시하지 않고, 실사 입력만 허용해야 합니다. 수정 SQL도 대상 세션·바코드·위치를 함께 검증해야 합니다.

2. **[높음] 추가 유통기한 실사가 재저장 시 삭제됨**
   
   - **파일:줄:** `inventory_logic.py:209`, `app.py:1962`, `app.py:2307`, `app.py:2367`, `app.py:1892`
   - **문제·근거:** 기존 실사 중 기준행과 일치하는 날짜만 입력란에 채웁니다. 기준에 없는 기존 실사 날짜는 추가 입력란에도 복원하지 않지만, 저장은 해당 대상의 실사를 전부 삭제하고 화면 입력만 다시 넣습니다.
   - **확인 방법:** 기준 날짜에 3개, 추가 날짜에 5개를 저장한 뒤 같은 상품을 다시 열어 전체 저장합니다. 함수 실행으로 기존 합계 8개가 미리 채운 합계 3개로 줄어드는 것을 확인했습니다. 화면·DB 재현은 미실행입니다.
   - **제안:** 기준에 없는 기존 실사 날짜도 추가 입력란에 복원하고, 사용자가 명시적으로 제거한 항목만 삭제해야 합니다.

3. **[높음] 업로드와 현장 기준행 편집이 서로 다른 잠금을 사용함**
   
   - **파일:줄:** `app.py:1453`, `app.py:2039`, `app.py:2115`
   - **문제·근거:** 업로드는 세션 잠금만 획득합니다. 실사 저장은 세션 공유 잠금도 획득하지만, 분할·날짜 변경·재정렬은 상품 대상 잠금만 획득합니다. 따라서 업로드와 기준행 편집은 직렬화되지 않습니다. 예를 들어 분할이 원본 수량을 읽은 뒤 덮어쓰기가 원본을 삭제하면, 분할은 새 행을 추가하고 원본 차감은 0행에 적용되어 기준수량이 증가할 수 있습니다.
   - **확인 방법:** 임시 PostgreSQL의 두 연결에서 분할을 원본 수량 조회 직후 대기시키고, 실사 없는 같은 세션을 덮어쓴 뒤 분할을 완료합니다. 최종 기준수량 합계와 중복 키를 확인합니다.
   - **제안:** 모든 현장 기준행 편집도 세션 공유 잠금 → 상품 잠금 순서로 획득하고, 원본 수정 건수가 1행인지 확인해야 합니다.

4. **[중간] 기존 중복행 때문에 무관한 신규 품목 추가까지 차단됨**
   
   - **파일:줄:** `inventory_logic.py:166`
   - **문제·근거:** 신규·기존 데이터를 합쳐 중복을 검사하므로, 기존 데이터 내부에만 있는 중복도 신규 업로드 충돌로 반환합니다. 기존 중복은 리포트에서 합산해 지원한다는 작업 지시와도 맞지 않습니다.
   - **확인 방법:** 기존에 B1 동일 키 2행을 두고, 겹치지 않는 B2 1행을 추가합니다. 실제 함수 실행에서 B1이 중복으로 반환되어 추가가 차단됨을 확인했습니다.
