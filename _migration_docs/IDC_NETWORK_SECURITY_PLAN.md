# IDC 목표 구성 및 네트워크 보안 계획

> 실제 IP/도메인/정책 명령은 아직 확정하지 않음. 여기 나온 IP·대역은 전부 예시 플레이스홀더이며, 실 적용 전 사용자 승인 및 실제 값 확정이 필요함.

## 1. 권장 OS 및 근거
- 웹 대시보드 + 데이터 파이프라인: **Linux (Docker Compose)** — §TARGET_OS_DECISION.md 근거 참조 (진짜 Windows 종속성 없음, 라이선스 비용 없음, 컨테이너 표준화)
- WMS 자동화(UPH 매크로, 사람 로그인 필요): 별도 **Windows 클라이언트/VDI** 유지 (IDC 내부망 또는 사내에 존치, 서버 이전 대상 아님)

## 2. 사양 권장 (초안, 트래픽 실측 전 추정치)
- CPU 4 vCPU / RAM 8GB / Disk 100GB SSD (현재 데이터량이 수십MB~수백MB 수준으로 작아 여유 있게 설정 — 실측 후 조정)
- 스토리지는 앱/DB/데이터 디렉터리를 논리적으로 분리 (아래 참고)

## 3. 디렉터리/계정 분리
```
/opt/scm-dashboard/app/       # 애플리케이션 코드
/opt/scm-dashboard/data/      # 업로드·다운로드 파일 등 영속 데이터
/var/lib/postgresql/          # DB (자체 호스팅 시) 또는 Supabase/원격 Postgres 그대로 사용
```
- 전용 서비스 계정(예: `scmapp`) 생성, 애플리케이션 프로세스는 이 계정 권한으로만 실행. sudo/관리자 권한 불필요
- DB 접속 계정도 애플리케이션 전용 계정으로 분리 (박스추천프로그램의 하드코딩 계정과 같은 관리자급 계정 재사용 금지 — 이번 조사에서 발견된 보안 위험 중 하나)

## 4. 자동 시작/복구
- systemd unit 또는 Docker `restart: always` — 부팅 시 자동 시작, 비정상 종료 시 자동 재시작
- 헬스체크 엔드포인트(Streamlit `/_stcore/health` 등) 기반 모니터링 연동

## 5. HTTPS Reverse Proxy
- Nginx 또는 Caddy를 프론트에 두고 Let's Encrypt(또는 사내 CA) 인증서로 TLS 종료
- 내부 Streamlit 프로세스는 127.0.0.1(로컬)에서만 리스닝, 외부에는 절대 직접 노출하지 않음

## 6. 포트 구성
| 서비스 | 리스닝 | 외부 노출 |
|---|---|---|
| Reverse Proxy (HTTPS) | 443 | O (창고/본사만) |
| Streamlit 앱 | 127.0.0.1:8501 (예시) | X |
| DB (자체 호스팅 시) | 127.0.0.1:5432 또는 내부망 전용 | X (앱 서버에서만 접근) |
| SSH/관리 | 22 | VPN 관리망에서만 |

## 7. IDC 방화벽 정책 원칙
- 사용자 웹 접속: **HTTPS 443만 허용**
- 가능하면 **창고·본사 고정 IP 또는 VPN 대역만** 인바운드 허용 (전체 공개 지양 — 현재 Streamlit Community Cloud 배포는 사실상 전 세계 공개 상태였으므로 IDC 이전 시 접근범위 축소가 핵심 개선점)
- RDP/SSH 등 관리 포트: **VPN 관리망에서만** 허용
- DB 포트: **애플리케이션 서버에서만** 허용, 그 외 인바운드 전면 차단
- 불필요한 인바운드 포트 전부 차단
- 아웃바운드: 다음 목적지에 대한 아웃바운드 허용 필요 (실제 IP/도메인은 승인 후 확정)
  - Supabase (클라우드 Postgres/API)
  - 별도 원격 PostgreSQL 서버 — **위치 미확인, 사용자 확인 필요**
  - WMS(이지어드민) — 파이프라인을 IDC로 옮길 경우 필요, **도메인/IP 미확인**
  - OS/패키지 업데이트 미러

## 8. 창고·본사 사용자 접속 방식
- HTTPS(443)로 Reverse Proxy를 통해서만 접속. 가능하면 사내 고정 IP 또는 VPN 클라이언트를 통해서만 도달 가능하도록 구성 (§ 추가 확인 필요: 창고/본사 고정 IP 확보 가능 여부)

## 9. 관리자 VPN 접속
- 관리 작업(SSH, DB 직접 접속, 배포)은 VPN을 통해서만 가능하도록 하고, 공인 인터넷에 관리 포트를 직접 노출하지 않음

## 10. DB 외부 직접 접근 차단
- Supabase/원격 Postgres 모두 애플리케이션 서버 IP만 allowlist에 등록 (Supabase는 대시보드에서 IP 제한 설정 가능 — 실제 설정 여부 **[미확인]**)
- 로컬에 DB를 두는 경우 방화벽으로 5432를 앱 서버 내부망 IP에서만 허용

## 11. 환경변수/비밀정보 관리
- 현재 발견된 문제: `박스추천프로그램/main.py`에 DB 비밀번호가 소스코드에 평문 하드코딩됨 (이번 조사 중 실수로 노출되어 즉시 로테이션 권고함)
- 개선안: 모든 비밀정보를 `.env` 또는 시크릿 매니저(예: Docker secrets, Vault)로 이전하고 코드에서 `os.getenv()`로만 참조. `.env`는 저장소에 커밋하지 않음(현재 Git 자체가 없으므로, 이번 기회에 Git 도입 + `.gitignore`도 함께 권장)

## 12. 로그
- OS 로그: journald(Linux) 표준 로테이션
- 앱 로그: 현재 `uph_agent.log`, `uph_download_macro.log`처럼 파일로 쌓는 방식 → 중앙 로그 수집(예: 파일 로테이션 + 필요 시 Loki/ELK) 도입 권장

## 13. 백업
- 일일 백업: DB 덤프(pg_dump) + `data/` 디렉터리 스냅샷을 매일 자동화
- 오프사이트 백업: IDC 외부(클라우드 스토리지 등)에 별도 보관 — 현재는 로컬 백업 자체가 없었으므로 신규로 설계 필요
