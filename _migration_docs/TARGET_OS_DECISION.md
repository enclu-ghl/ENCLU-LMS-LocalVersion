# 신규 IDC 서버 OS 판단

전제: 마이그레이션 대상은 **웹 대시보드(Streamlit app.py) + 그것이 읽는 Supabase/원격 Postgres 데이터 파이프라인**으로 한정한다 (Tkinter 데스크톱 도구 4종은 성격상 서버 이전 대상이 아니라고 판단 — 사용자 확인 필요, §10 참고).

## 비교 대상
- A. Linux 서버 + Docker Compose
- B. Linux 서버 + 네이티브 서비스(systemd 등)
- C. Windows Server

## A. Linux + Docker Compose

| 항목 | 내용 |
|---|---|
| 호환 가능성 | 높음. Streamlit/pandas/sqlalchemy/psycopg2/pyzbar/opencv-headless 모두 Linux·컨테이너 지원 우수 |
| 변경 범위 | 하드코딩 경로 제거, Dockerfile/compose 작성, `.env`를 컨테이너 환경변수로 전환 |
| 필요 라이선스 | 없음 (OSS만 사용) |
| 운영 안정성 | 높음 — 컨테이너 격리, 재현 가능한 빌드 |
| 자동 시작/장애 복구 | `restart: always` + systemd 하나로 컨테이너 엔진 자체를 관리 → 우수 |
| 백업·복원 | 볼륨/DB 스냅샷 표준화 용이 |
| 보안 관리 | 이미지 최소화, 정기 base image 업데이트로 관리 |
| 예상 작업시간 | 중간 (Docker화 학습/디버깅 포함, 2~4일 추정) |
| 주요 위험 | 팀에 Docker 운영 경험이 없다면 초기 러닝커브. UPH 파이프라인(Selenium)은 컨테이너 안에서 헤드리스로 재작성해야 하며, WMS 로그인 자동화 문제는 그대로 남음 |
| 롤백 방법 | 컨테이너 중지 후 기존 Windows PC 프로세스로 즉시 복귀 (원본 미변경 원칙 유지 시 안전) |

## B. Linux + 네이티브 서비스

| 항목 | 내용 |
|---|---|
| 호환 가능성 | A와 동일하게 높음 |
| 변경 범위 | A와 유사하나 Docker 대신 systemd unit 작성, venv/패키지 직접 관리 |
| 필요 라이선스 | 없음 |
| 운영 안정성 | 준수하나 OS 패키지·Python 버전 관리를 서버에서 직접 해야 해 환경 드리프트 위험이 A보다 약간 높음 |
| 자동 시작/장애 복구 | systemd `Restart=on-failure`로 가능 |
| 백업·복원 | 표준 파일/DB 백업 스크립트 필요 (Docker 볼륨만큼 정형화되진 않음) |
| 보안 관리 | OS 패키지 보안 업데이트를 직접 관리해야 함 |
| 예상 작업시간 | 낮음~중간 (Docker 학습 불필요, 1~3일 추정) |
| 주요 위험 | A와 동일하게 Selenium/WMS 로그인 문제는 미해결. 팀이 향후 컨테이너 표준화를 원한다면 이중 작업이 될 수 있음 |
| 롤백 방법 | A와 동일 |

## C. Windows Server

| 항목 | 내용 |
|---|---|
| 호환 가능성 | 매우 높음 — 현재 코드가 이미 Windows에서 동작 중이므로 이식 작업이 사실상 최소 |
| 변경 범위 | 하드코딩된 사용자 경로(`C:\Users\enclu\...`)만 서비스 계정 경로로 정리하면 됨. GUI 도구도 그대로 살릴 여지가 큼 |
| 필요 라이선스 | Windows Server CAL/OS 라이선스 비용 발생 (Linux 대비 확실한 비용 증가 요인) |
| 운영 안정성 | 준수하나, Linux 대비 컨테이너/IaC 생태계가 약함 |
| 자동 시작/장애 복구 | NSSM 또는 Windows 서비스 등록 + `sc failure` 자동재시작 설정으로 가능 |
| 백업·복원 | Windows 백업 도구 또는 스크립트 기반, Linux 대비 표준화된 스냅샷 생태계는 약함 |
| 보안 관리 | Windows Update, Defender 등 익숙한 도구 사용 가능 |
| 예상 작업시간 | 가장 짧음 (현재 코드 변경 최소, 1~2일 추정) |
| 주요 위험 | 라이선스 비용 지속 발생. 장기적으로 Docker/클라우드 네이티브 생태계와 멀어짐 |
| 롤백 방법 | 가장 단순 (현재 환경과 거의 동일) |

## 권고안

- **웹 대시보드 + 데이터 파이프라인 부분**: **B(Linux 네이티브) 또는 A(Docker)** 권장. 근거: §WINDOWS_DEPENDENCY_REPORT.md에서 확인했듯 이 부분은 COM/레지스트리/전용장비 등 진짜 Windows 종속성이 없고, DB도 이미 클라우드형이라 "현재가 Windows라서" Windows Server를 고를 이유가 약함. 장기 운영 안정성·비용(라이선스 없음)·컨테이너 표준화 이점을 고려하면 **A(Docker Compose)** 를 1순위로 제안.
- **Selenium 기반 WMS 자동화(UPH 매크로)** 는 OS 선택과 무관하게 "사람이 로그인해야 하는" 구조가 근본 문제이므로, 어떤 OS를 고르든 별도로 (1) WMS API 연동 가능 여부 확인, 또는 (2) 이 부분만 별도의 상시 로그인 Windows 클라이언트/VDI로 유지하는 하이브리드 구성이 필요함. 이 부분만 놓고 보면 **C(Windows)** 성격을 일부 유지해야 할 가능성이 높음 — 즉 "전부 Linux로 이전"을 강행하지 않고, 웹/DB 파이프라인은 IDC Linux 서버로, WMS 자동화는 별도 Windows 클라이언트로 분리하는 **혼합 구성**을 권고.
- Tkinter 데스크톱 도구 4종은 애초에 "서버"가 아니라 "직원 PC에서 쓰는 도구"이므로 IDC 이전 대상에서 제외하고 그대로 각자 PC에 유지하는 것을 제안 (§10 질문에서 최종 확인 필요).
