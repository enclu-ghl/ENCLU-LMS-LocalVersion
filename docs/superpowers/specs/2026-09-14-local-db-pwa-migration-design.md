# 로컬 DB 전환 + PWA 전환 설계

- 작성일: 2026-09-14
- 상태: 설계 승인됨, 세부 실행계획 작성 예정

## 배경 / 문제의식

지금 모든 프로그램(UPH 시스템, 주문파일정리 프로그램, 박스추천프로그램, `app.py` 웹앱)이
Supabase(UPH·주문파일정리·app.py 공유) + 별도 원격 PostgreSQL(박스추천프로그램)을 쓰고 있는데,
Supabase 인스턴스가 t4g.nano급 최소 사양이라 행사 등 트래픽이 몰릴 때마다 반복적으로
timeout·circuit breaker·저장용량 한계 문제가 발생해왔다(2026-09 초 세션에서 여러 차례 확인).
근본 해결은 유료 티어 업그레이드지만, 사용자는 대신 **모든 프로그램의 DB를 현재 PC의 로컬
PostgreSQL로 통합**하는 방향을 택했다. 동시에 `app.py`(현재 Streamlit Community Cloud 웹앱)를
**PWA(홈화면 설치 가능한 웹앱)** 로 전환해 폰/PC 양쪽에서 "다운로드"된 것처럼 쓸 수 있게 한다.

## 범위

**대상**: 아래 4개 프로그램 전부, 하나의 로컬 PostgreSQL로 통합
- UPH 시스템 (`watchdog_agent.py`, `uph_download_macro.py`) — 현재 Supabase
- 주문파일정리 프로그램 (`file_splitter_gui.py`) — 현재 Supabase
- 박스추천프로그램 — 현재 별도 원격 PostgreSQL
- `app.py` (재고조사/무게구간/UPH 현황판/재고할당/소모품관리 등) — 현재 Supabase, 현재 Streamlit
  Community Cloud에 배포됨

**제외**: 송장짜르기(주문파일정리 프로그램의 엑셀 분리 기능)는 애초에 PC 전용 작업이라
모바일화 대상이 아님. 이번 전환은 DB 위치와 `app.py`의 배포/접속 방식만 바꾸는 것이지,
각 프로그램의 기능 자체를 바꾸는 게 아니다.

## 아키텍처

```
[현재 PC = 서버]
  PostgreSQL(로컬)  ←── 4개 프로그램 전부 접속 (.env의 DATABASE_URL만 교체)
  app.py를 이 PC에서 직접 서빙 (streamlit run, Streamlit Cloud 대체)
       │
       └─ Tailscale (메시 VPN) ── 포트포워딩 없이 외부에서도 안전 접속
                │
        [폰 브라우저] [다른 PC 브라우저] → PWA로 홈화면에 설치
```

### 핵심 변경 3가지
1. **DB**: Supabase + 원격 Postgres(박스추천) → 이 PC의 로컬 PostgreSQL 하나로 통합.
   대부분 프로그램은 SQLAlchemy로 이미 `DATABASE_URL` 기반이라 연결 문자열만 바꾸면 됨
   (SQL 문법은 표준 Postgres라 호환).
2. **웹앱 호스팅**: Streamlit Community Cloud → 이 PC에서 직접 실행. 로컬 전용 DB는
   외부 클라우드에서 접속 불가능하므로 필수.
3. **원격 접속**: Tailscale 설치(서버 PC + 사용자 폰 + 다른 PC들). 외부에서도 필요
   (사용자 확인: "와이파이 안에서만 쓰지 않을 것 같다, 외부 접속 필요").

### 결정된 사항
- 서버 머신: 새로 구매하지 않고 **현재 PC를 그대로 서버로 사용**
- 원격 접속 방식: **Tailscale** (포트포워딩·공인IP 노출 없이 안전)
- 앱 형태: **PWA 우선** (Streamlit 코드 재사용, 개발량 최소화). 바코드 스캔(재고조사)이
  실제로 병목이면 **그 기능만 나중에 네이티브 모바일 앱으로 분리** 검토 — 지금 전체를
  네이티브로 새로 짜지 않음(백엔드 API 신규 구축 + 프론트 전면 재작성이라 현재 개발
  리소스로는 과함)

## 리스크

- **이 PC가 SPOF(단일 장애점)가 됨** — 꺼지거나 재부팅되면 전체 시스템 정지. Supabase는
  자동 백업/이중화가 있었지만 로컬은 없음 → **1단계에서 자동 일일 백업(pg_dump) 구축을
  최우선으로 함**
- Streamlit은 PWA 전용 프레임워크가 아니라서 manifest/서비스워커 붙이는 부분은 구현
  단계에서 세부 조정 필요 (막히면 대안: 정적 래퍼 페이지로 manifest 서빙)
- 마이그레이션 중 실서비스 중단 없이 전환해야 함 — 프로그램별로 순차 전환 + 병행 운영
  기간 필요

## 단계별 계획 (개요)

| 단계 | 내용 |
|---|---|
| 1 | 로컬 PostgreSQL 설치·DB 생성, 자동 백업 루틴 먼저 구축 |
| 2 | Supabase + 원격 Postgres → 로컬로 스키마+데이터 전체 이전, 행수 대조 검증 |
| 3 | 프로그램별 순차 전환 (UPH → 주문파일정리 → 박스추천), 각각 테스트 |
| 4 | `app.py`를 이 PC에서 직접 서빙으로 전환, 사내망 접속 확인 |
| 5 | Tailscale 설치·설정, 외부 접속 테스트 |
| 6 | PWA 레이어 추가(manifest/서비스워커), 폰에서 홈화면 설치 확인 |
| 7 | 일정 기간 병행 운영 후 문제 없으면 Supabase·원격 Postgres 해지 |

세부 실행/개발 순서는 별도 구현 계획 문서에서 작성한다 (writing-plans 단계).
