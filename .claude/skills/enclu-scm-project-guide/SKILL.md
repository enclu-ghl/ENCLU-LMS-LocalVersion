# ENCLU SCM 물류통합시스템 작업 매뉴얼

이 프로젝트는 하나의 저장소가 아니라 **여러 개의 독립된 GitHub 저장소**가 한 로컬 폴더
(`통합시스템\`) 안에 나란히 들어있는 구조다. 폴더만 보고 "이 프로젝트는 저장소 하나"라고
착각하면 엉뚱한 저장소에 푸시하거나, 이미 있는 원격 변경사항을 놓치고 충돌을 낼 수 있다.

## 저장소 지도

| 로컬 폴더 | GitHub 저장소 | 비고 |
|---|---|---|
| `통합시스템\` (루트: 허브런처, 박스추천프로그램, UPH 시스템, 자동 매칭 프로그램, 주문파일정리 프로그램, `_migration_docs`) | `enclu-ghl/ENCLU-LMS-LocalVersion` | 로컬에서만 도는 프로그램들 |
| `통합시스템\웹으로 진행 중인 건\` (app.py — 재고조사/무게구간/UPH 현황판/소모품관리 허브) | `enclu-ghl/ENCLU-LMS` (예전 이름 `inventory-check`, 이름 바뀜 — 구 URL도 리다이렉트되어 그대로 동작함) | **Streamlit Community Cloud에 배포됨.** 코드를 push해도 앱이 그 즉시 최신 커밋을 못 받아오는 경우가 있었음 — 이상하게 옛날 숫자/동작이 보이면 share.streamlit.io에서 앱을 reboot 해보라고 안내할 것 |

새 폴더를 건드리기 전에는 항상 `git remote -v`로 그 폴더가 어느 저장소에 연결돼 있는지
먼저 확인한다. 두 저장소는 서로 완전히 무관하므로, 한쪽에 커밋한다고 다른 쪽에 반영되지 않는다
(예: `watchdog_agent.py` 수정은 LMS-LocalVersion에, `app.py` 수정은 ENCLU-LMS에 각각 push해야 함).

## git 작업 원칙

- **로컬 파일 수정은 자유롭게, 바로 진행한다.** 프로그램 실행에는 git과 무관하게 지장이 없다.
- **commit/push는 매번 사용자에게 먼저 물어보고 진행한다.** (사용자가 명시적으로 확인한 선호 —
  실수로 이상한 버전이 원격에 올라가는 걸 막고 싶어함)
- push 전에는 `git status`로 무엇이 올라가는지 항상 확인한다. 특히 `.env`, `venv/`,
  `__pycache__`, 로그(`*.log`)·캐시DB(`*.sqlite3`), 실제 다운로드된 업무 데이터
  (`UPH 시스템\Download the Uph file\*`), 실제 DB 서버 설정(`pg_hba.conf`, `postgresql.conf`)은
  절대 커밋되면 안 된다 — 이미 `.gitignore`에 등록돼 있지만, 새 폴더/파일을 추가할 때는 같은
  기준으로 점검할 것.
- push 시 remote가 앞서 있으면(다른 세션/GitHub 웹 UI에서 직접 커밋된 경우가 실제로 있었음)
  절대 강제로 덮어쓰지 말고, `git fetch` → 변경 내용 확인 → `git pull --no-edit`(또는 merge)로
  안전하게 합친 뒤 다시 push한다.

## 비밀정보(DB 접속정보 등) 처리 원칙

- DB 접속정보(호스트/계정/비밀번호)를 코드에 하드코딩하지 않는다. `python-dotenv`의 `load_dotenv()`
  + `os.getenv()`로 읽고, 실제 값은 각 프로그램 폴더의 `.env` 파일(항상 `.gitignore` 대상)에 둔다.
  과거 `박스추천프로그램\main.py`에 실제 운영 DB 비밀번호가 `os.getenv()`의 기본값으로 그대로
  박혀있던 사고가 있었음 — 새 코드를 작성하거나 기존 코드를 커밋하기 전에 비슷한 패턴이 없는지
  훑어본다 (`grep -i "password\|postgresql://"` 등으로 빠르게 확인 가능).
- DB는 두 종류를 쓴다: **Supabase**(UPH 시스템, 주문파일정리 프로그램, `app.py`의 UPH 현황판이
  공유해서 씀 — `order_status_log` 테이블 등)과 **별도 원격 PostgreSQL**(박스추천프로그램 전용,
  이미 가동 중인 서버).

## UPH 대시보드류 숫자가 이상할 때 진단하는 법

"잔여 건수가 WMS랑 다르다" 같은 신고가 들어오면, 추측하지 말고 **Supabase를 직접 SQL로 조회해서
실측 검증**한다. `.env`에 `DATABASE_URL`이 있으니 `sqlalchemy.create_engine()`으로 바로 붙을 수
있다. 이 프로젝트에서 실제로 잡았던 버그들이 전부 이런 방식(추측 후 대시보드 코드만 보고 고치는 게
아니라, DB에서 실제 order_key/detected_at을 찍어보고 패턴을 확인)으로 확정됐다:

1. **`order_key`(관리번호_상품코드) 불일치**: WMS가 같은 상품의 상품코드를 어떤 날은 `3727`,
   어떤 날은 `03727`처럼 앞자리 0 유무를 다르게 내려줘서, 같은 상품이 서로 다른 키로 갈라져
   상태 추적이 끊기는 문제가 있었다. `app.py`의 잔여 집계 쿼리는 상품코드 앞자리 0을 무시한
   `norm_key`로 묶어서 이를 해결했고, `watchdog_agent.py`도 앞으로 들어오는 데이터부터는
   정규화된 키로 저장하도록 고쳐뒀다. 비슷한 "같은 실물인데 필드 표기가 달라서 키가 갈라지는"
   패턴이 또 나타날 수 있으니 의심해볼 것.
2. **watchdog가 조용히 멈춤**: `uph_download_macro.py`는 정상적으로 계속 도는데
   `watchdog_agent.py`(감시 에이전트)가 파일 처리 중 예외로 감시 스레드 자체가 죽어서, 프로세스는
   살아있지만 몇 시간째 새 파일을 전혀 처리 안 하고 있던 적이 있다. 증상은 "동별로 최근 몇 시간
   갱신이 전혀 없는데 다운로드 폴더엔 새 파일이 계속 쌓여있음". `SELECT MAX(detected_at) FROM
   order_status_log GROUP BY dong`으로 동별 최신 갱신 시각을 찍어보면 바로 확인된다. 지금은
   예외를 잡아 로그만 남기고, observer가 죽어있으면 자동 재시작하는 자가복구 로직이 들어가 있다.
3. **오래된 미배송 건이 조회 범위 밖으로 밀려남**: `uph_download_macro.py`는 발주일 -4일~오늘만
   조회하는데, 그보다 오래전에 발주됐지만 아직 미배송인 주문은 그 범위를 벗어나면 다시는
   재조회되지 않아 상태 변화(배송완료/취소)를 영영 놓친다. 지금은 -21일~-5일 범위를 6시간마다
   추가로 재확인하는 회차가 들어가 있다(`RECON_START_OFFSET_DAYS` 등).

진단할 때 유용한 패턴: `order_status_log`에서 특정 동/송장번호로 전체 이력을 시간순으로 찍어보고,
"같은 실물인데 order_key가 두 개로 갈라져 있는지", "가장 최근 detected_at이 다른 동/데이터에 비해
비정상적으로 오래됐는지"를 먼저 확인한다.
